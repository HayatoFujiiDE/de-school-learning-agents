# コンテンツファクトリー 設計書 v1

2026-11-04 版。DE-SCHOOL「学びのAIエージェント」構想のうち、共通素材を作り続ける「コンテンツファクトリー」の設計。人（運営・サポーター）と、別企画を実装する Codex の両方が読む前提で書く。

上位の設計正本は統合構想設計案 v1.0（2026-11-03、非公開）。本書はその「詳細7 コンテンツファクトリーとライブラリ」「詳細8 記憶と情報共有」「詳細2 どのAIが何を担当するか」を実装の形に落としたもの。食い違いがあれば設計正本が優先する。

## 1. 一文で

3 つの入口から「提案箱」に題材が集まり、運営が採択したものを職人（Claude Managed Agents）が「編集基準」を読んでから作り、別の検証係が出典を開き直して確かめ、運営が 6 項目で確認したものだけが子どもに届く。運営の判断は編集基準に貯まり、工程は順にエージェントの自走へ移す。

## 2. 登場人物

| 役割 | 実体 | 費用の目安（定価・未計測） |
|---|---|---|
| 提案を持ち込む 3 入口 | 子どもとのやり取り（バディ → サポーター一読）/ 収集部隊（Cloudflare 定期実行 + 無料の情報源 + X 検索）/ エージェント会議（月 2 回、Messages API 1 回） | 月 $5 |
| 提案箱と採択 | Cloudflare Worker の管理画面。採択は運営（段階 1） | $0 |
| 職人 | Claude Managed Agents（サンドボックス付き）。作る前に「確認したいこと」を 2〜3 問返す。編集基準を毎回読む | 1 本 $2〜3 |
| 検証係 | 制作とは別文脈の Claude Opus 5.5（Messages API + web_fetch / web_search）。出典を自分で開き直し、主張ごとに 確か / 仮説 / 未確認 / 矛盾 を付ける。毎回必ず通す | 1 本 $0.5〜1 |
| 受付と倉庫 | Cloudflare Worker + D1 + R2。状態管理、出典 URL の機械照合、承認の記録、配信 | ほぼ $0 |
| 確認する人 | 運営。設計正本の 6 項目チェック。承認 / 差し戻し / 却下 / 停止 / 前版へ戻す | 時間 |
| 振り返り係 | 週 1 の Messages API 1 回。差し戻し理由・承認の傾向から編集基準の改訂案を出す。運営が承認したものだけ効く | 月 $1 |
| 番人（バディ側） | Claude Haiku 5.5。バディがその場で生成した文を出す直前に軽く見る | 1 回 1 円未満 |

Managed Agents（作業場つきの長い自律ループ）を使うのは職人だけ。他は Cloudflare の定期実行 + 1 回の API 呼び出し、または LLM なしのコードで行う。理由は費用（Managed Agents は稼働時間とサンドボックスに課金される）と、設計正本の「七つの別製品ではない」。

## 3. 1 本ができるまで

1. 提案箱から採択し、型を選ぶ（§5）
2. 職人が編集基準と型別の採点表（rubric）を読み、確認したいことを 2〜3 問返す。運営が答える
3. 職人が調査 → 構成（触れるものを先頭に置く）→ 制作（小学生表示・中学生表示の両方、変奏 §6）→ 自分で動作確認（コードを実行、HTML 構文、リンク到達、禁止語、個人名）
4. 検証係が別文脈で全主張を検証。受付が出典 URL を機械照合（URL を本当に開いたか、引用がそのページにあるか）
5. 運営が確認。差し戻しは理由つきで職人へ戻る。承認で「利用できる」
6. 差し戻し理由と承認はすべて編集基準の材料として貯まる

承認したあとに誤りが見つかったら「停止」で一覧から即座に消え、「前の版へ戻す」で以前承認した版に差し替える。

## 4. 3 つの入口 + 提案箱

| 入口 | きっかけ | 実体 | 気をつける点 |
|---|---|---|---|
| 1) 子どもとのやり取り | バディが会話中に「素材があるといい」と気づく | バディ側で Haiku 5.5 が個人を含まない提案文（題材・つながる概念・何が足りなかったか・年齢帯）を起こす → サポーターが一読して提案箱へ | 設計正本「個人を含めず整理して渡す」。子どもの名前・会話そのものは入れない |
| 2) 常時収集部隊 | 定期巡回（週 1 から） | Cloudflare Cron → 無料の情報源（各社 changelog・GitHub Releases・arXiv RSS）+ xAI の X 検索（1,000 投稿 $5）または X API（1 投稿 $0.005）→ Haiku 5.5 が「新規 / 改善 / 捨て」に仕分け → 提案箱 | X や Web は発想の入口であって根拠ではない |
| 3) エージェント会議 | 月 2 回 | Sonnet 5.5 への 1 回の呼び出しで 4 視点（調査 / 教材研究 / 技術表現 / 検証）の意見と優先順位を構造化出力。Batch API で半額 | 会議は「何を作るか」の材料。「正しいか」は決めない |

改善候補の突き合わせは LLM なし。素材に「使った技術・モデル」（tech_dependencies）を記録しておき、収集部隊の「技術更新」提案と DB で突合する（例: 3D 生成の質が上がったら、3D で作った素材が改善候補に並ぶ）。

### 「今日のお題」

素材の一種（型 6）。週 1 回の職人セッションで 7 本まとめて作り、運営が月曜に確認し、火曜から 1 日 1 本ずつ Worker が自動で「利用できる」に切り替える。毎朝生成しないのは「子どもに届く前に人が確認する」を守るため。

- 4 入口必須: 「短い動画を見る」「実物を探す」「試して遊ぶ」「作ってみる」。説明文は入口の後ろ
- 動画は公式チャンネルの埋め込みのみ。ライセンスを出典に記録
- 屋外・生き物・刃物などは「サポーター確認が要る」印を必須にする（設計正本「写真だけで安全性を確定しない」）
- 個別化（好きに近い / 少し隣 / 意外）はバディ側の責務。承認済みの束を読むだけ

## 5. コンテンツの型（8 種）と部品

| 型 | 中身 | 例 | 子どもの入口 |
|---|---|---|---|
| 1 活動レシピ | 材料・手順・所要時間・区切り・続きの候補・安全 | ダンボール工作、3D ペン | 手順 1 から始める |
| 2 作例と見本 | 真似して動かせる完成物 + 変えられる箇所 | Python ゲームの見本コード、マイクラのコマンド例 | 見本を動かす・1 箇所変える |
| 3 説明と図解 | 短い説明 + 図（SVG）+ 確か / 仮説の区別 | レッドストーン回路の仕組み、赤血球の役割 | 図を見る・問いに答える |
| 4 動かせるもの | 単体 HTML/JS のシミュレーション | 血液の流れ、回路の電気 | スライダーを触る |
| 5 見る | 公式動画の埋め込み + 見どころ + 出典 | 特撮の作り方 | 2 分見る |
| 6 今日のお題 | タイトル + 4 入口 | 季節の生き物 | 4 入口のどれか |
| 7 基礎学習の足場 | 概念 ↔ 活動の対応 + 既存教材への入口 | 分数 ↔ マイクラの建築 | 活動から概念へ（v1 では別企画が担う。§9） |
| 8 世界との接続 | 場所・実物・季節の観察ガイド + 安全の印 | 近所の植物、夜空 | 外で確かめる |

1 つの題材は複数の部品（part）を持つ（例: 「赤血球」= 説明と図解 + 動かせるもの + 見る）。小さな単位（15〜30 分で触れ切れる）を作り、束ね方（順番・続き）は別レコード（bundle）で持つ。

型ごとに rubric 1 枚、注文票（brief）の質問、確認画面の重点項目を変える。例: 型 2 は「見本が実行できる・変えられる箇所が 3 つ明示」、型 4 は「操作 1 つで見た目が変わる・外部ライブラリなし 1 ファイル」、型 6 は「4 入口」、型 8 は「サポーター確認の印」。

v1 で作らないもの: 動画・画像・3D モデル・Minecraft ワールドの生成。公式素材の参照か人の手作業にする。

## 6. 変奏（個別化の肝）

ファクトリーは素材ごとに次の 4 層の変奏を作り、変奏ごとに rubric と検証を通す。

| 層 | 内容 |
|---|---|
| 関心別の入口・例 | カタログのカテゴリ別（マイクラ / プログラミング / ものづくり / デジもの / 画像・動画 / 絵）に、同じ概念への入口を 2〜3 通り |
| 説明量 2 段 | 短い / 詳しい |
| ゲーム的な形 | お題・クイズ・「なし」を当てる形など、同じ内容を遊びの形にした版を 1 つ |
| 小学生 / 中学生表示 | 語彙・ふりがな・説明量・問いかけ |

## 7. バディが子どもごとに変える時の線引き

バディ（個別の調理場）は、承認済み素材を子どもに合わせてその場で組み替え・生成してよい（関心・体験・習熟・心理・志向性でアプローチや解説を変える）。ただしミスを構造で減らす。

1. 職人の成果物に必ず `claims.json`（検証済みの主張一覧。確か / 仮説 / 未確認 の印つき）と `adapt-rules.md`（変えてよい範囲・変えてはいけない事実）を付ける
2. バディは両方を文脈に入れて生成する
3. 出す直前に番人（Haiku 5.5）が「claims にない事実を足していないか」「禁止語」「個人名」を判定する。不合格なら承認済みの変奏にフォールバックする
4. 生成ログはバディ側に保持する（子どものデータなのでファクトリーへは流さない）
5. 検証係が日次で抜き取り（個人を含まない形）を確認し、問題は改善提案として提案箱へ戻す

## 8. 編集基準と自走への移し方

運営の回答・承認・差し戻し理由は「編集基準」として貯まり、職人は毎回それを読んでから作る。週 1 の振り返り係が改訂案を出し、運営が承認したものだけが次回から効く。

| 段階 | 運営がやること | エージェントがやること | 移行条件（案） |
|---|---|---|---|
| 1（最初の 10〜20 本） | 採択・質問への回答・承認、全部 | 作る・検証する | 開始時 |
| 2 | 新規の採択と承認。基準で答えられる質問は返ってこなくなる | 改善提案の採択、基準の改訂案 | 差し戻し率が一定以下を N 本続けたら |
| 3 | 承認（子どもに出す判断）だけ | 採択・質問の自己解決・制作・検証・基準改訂案 | 同上 |
| 4 | 抜き取りで確認 | 基準を満たしたものを自動で「利用できる」へ | 「人が確認する範囲」を型・条件で基準に明記してから |

段階は戻せる。設計正本の「どの内容で人の確認が必須かは公開前に決める」は段階 4 の前提条件として扱う。

## 9. 別企画（基礎学習・eboard 型）との境界

基礎学習教材（eboard 型。達成率が測れるもの）は Codex が実装する別企画。ファクトリー v1 は型 7 を作らず、学習指導要領コード（文科省公開 Excel）を素材の「つながる概念」の共通キーにする。別企画ができたら、その単元の中身をファクトリーが作り、改善を回す。詳細は `docs/handoff-for-codex-basic-learning.md`。

## 10. 子どもへの見せ方の約束

- 達成率（%）は子どもにも見せる。ただし「点数・ランキング・順位・評価・成績・レベル」の語は子ども画面で使わない
- 未確認の素材は構造上、子ども向け API に出ない（「利用できる」かつ承認済み版のみ返す）
- 子どもの会話・記録はファクトリーに入らない。ファクトリーの DB に子どもを表す列を作らない。バディ側は読むだけ（一方向）

## 11. 予算（段階 1 = 月 $100）

制作 10〜15 本 $30 + 検証 $15 + 入口 $5 + 振り返り $1 = 月 $50 前後（定価の机上見積。最初の 10 本で実測して置き換える）。上限は 3 段: 1 セッションの上限、1 日の上限、月の上限（Anthropic Console の支出上限）。どれかに当たったら新しい仕事を始めず、管理画面に「止まっています」と出す。上限は人の操作でのみ増やす。

## 12. 技術の要点（実装者向け）

- Cloudflare: Worker 1 本（HTTP + cron + 管理画面の静的ファイル）、D1（状態・台帳）、R2（成果物）、Cloudflare Access（管理画面の保護）。Queues / Workflows / KV は v1 では使わない
- Managed Agents: agent 1 定義（`factory/claude/agents/material-maker.md`、`ant apply` でファイル管理）、1 素材 = 1 セッション、`initial_events` で brief + `user.define_outcome`（rubric）を渡し、`budget` を必ず付ける。通知は Console 登録の webhook（HMAC 検証、薄い payload、順序保証なし）+ 10 分ごとの cron 照合
- 秘密（Anthropic API key、webhook 署名鍵、X/xAI の鍵）は `wrangler secret put` のみ。職人の作業場には渡さない
- 「利用できる」への遷移は、運営の承認記録の挿入と同一トランザクションでのみ起きる。職人側に遷移手段はない
- 実装契約は `CONTRACT-factory.md`（凍結後）
