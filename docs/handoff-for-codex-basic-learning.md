# 基礎学習教材（eboard 型）企画の引き継ぎ資料 — Codex 向け

2026-11-04 版。DE-SCHOOL「学びのAIエージェント」構想の中で、基礎学習教材を別企画として Codex に実装してもらうための資料。運営（藤井）の発言はできるだけ趣旨そのまま残す。全体構想の設計正本は統合構想設計案 v1.0（非公開）、コンテンツファクトリーの設計は `docs/content-factory-design.md`。

## 1. 企画の位置づけ

- 学びのAIエージェントは、子ども専属のバディエージェント、子ども同士の協働、サポーター、システムフィードバック、コンテンツファクトリーの 5 要素でできている
- 基礎学習教材は、設計正本「詳細5 基礎学習と未知との出会い」の「活動と概念の両方から入れる」「学習指導要領とのつながり」を担う
- 運営の決定: **「Eboard系は自作しよう。Eboard参考にと、ただ、学習指導要領のエクセルでチェックリスト的に内容がまとまっているやつがあるからあれを参考に。特に基礎学習教材はEboardの達成率測れるやつめちゃいい」**
- **「Eboardのやつは別で企画。Codexに実装してもらう」**。コンテンツファクトリー（Claude Managed Agents で素材を作る側）とは別のコードベース・別の企画として進める
- ファクトリーとの関係: 「Codexに任せて実装。そのコンテンツに合わせてファクトリーで適宜・調整改善を続ける」。つまり、まず Codex が教材の器と最初の中身を作り、その後ファクトリーが中身の改善を回す

## 2. 参考にするもの

| 参考 | URL | 何を参考にするか |
|---|---|---|
| eboard | https://www.eboard.jp/list/ | 単元の並び、短い説明 + 練習問題 + 達成率の構成 |
| 学習指導要領コード（文科省） | https://www.mext.go.jp/a_menu/other/data_00001.htm | Excel のチェックリスト。単元・到達点の骨組みと、素材を結ぶ共通キー |

## 3. 運営が決めた方針（発言の趣旨そのまま）

1. **最初の範囲**: 小学算数の 1 学年分で型を固める
2. **「できたか」の確認**: 練習問題の正答による機械判定と、バディとの会話で説明できたかの確認の **両方**。さらに「ゲーム的な学びとかも含めて、うまく学びの形を作りたい」
3. **達成率**: 「子どもにも達成率（%）を見せる」。ただし子ども画面で「点数・ランキング・順位・評価・成績・レベル」の語は使わない（既存の子ども向け画面の契約と揃える）
4. **動的な最適化**: 「コンテンツファクトリーで質の改善回して適宜中身改定＋ユーザーによってコンテンツを動的に変える（関心、体験、志向性など含めてアプローチを変えたり、解説を変えたりして最適化する）」
5. **質の基準**（ファクトリーと共通）: 説明より先に「触れるもの」がある / 小学生・中学生の両表示を最初から持つ / 内容の確からしさは別のエビデンス検証エージェントを毎回必ず通す
6. **変奏を多層に**: 関心別の入口・例（マイクラ / 工作 / 絵などカタログのカテゴリ別）、説明量 2 段（短い / 詳しい）、ゲーム的な形（お題・クイズ・「なし」を当てる形）、小学生 / 中学生表示。「最適化の肝だからここはしっかり多層的に質高くつくろう」
7. **バディがその場で変える範囲**: 「B で事後チェックでいい。ただ、そんなミスらないように軽くチェックとか出す時にできる構造にできているといいけど」。つまり、その場生成を許すが、出す直前の軽いチェックと事後の抜き取り確認を構造として持つ

## 4. ファクトリー側が約束する「素材の形」（教材側はこれを読む）

| ファイル / 項目 | 内容 |
|---|---|
| `claims.json` | 検証済みの主張一覧。各主張に 確か / 仮説 / 未確認 の印と出典 ID |
| `adapt-rules.md` | バディが変えてよい範囲（言い換え・例の差し替え・説明量）と、変えてはいけない事実 |
| 変奏（variants） | 関心別 × 説明量 2 段 × ゲーム的な形 × 小中表示 |
| つながる概念 | 学習指導要領コード（共通キー）とカタログの取り組み ID |
| 出典と利用条件 | 一次資料の URL・取得日・引用・ライセンス |
| 確認状況 | 確認済み / 未確認の範囲。「利用できる」かつ承認済み版だけが配信 API に出る |

教材側がその場で解説を生成する時は、`claims.json` と `adapt-rules.md` を文脈に入れ、出す直前に軽い番人（Haiku 5.5 程度）で「claims にない事実の追加・禁止語・個人名」を判定し、不合格なら承認済みの変奏にフォールバックする。生成ログは教材側（子どものデータ）に保持し、ファクトリーへは個人を含まない改善提案だけを返す。

## 5. 守ること（設計正本由来）

- 子どもの会話・個別記録を共通素材に混ぜない。ファクトリーへ返す改善情報は個人を含めず整理する
- 未確認の素材が自動で子どもへ流れない
- 本人の訂正・例外を反映し、過去の好みで挑戦を狭めない（「A だから B はできない」としない）
- 「毎日やる」を義務にしない。休む・任せる・今日は終える、を選べる
- 録音は使わない。根拠はアプリ内の会話・活動・作品・予定・サポーターの入力

## 6. 教材側で決めてよいこと・運営に聞くこと

- 決めてよい: 画面構成、問題の形式、達成率の計算方法、データの持ち方（ただし学習指導要領コードを単元の主キーにすること）
- 運営に聞く: 対象学年の拡張順、ゲーム的な形の具体案、達成率の見せ方の文言、サポーター画面に出す数値

## 7. 用語

- バディエージェント: 子ども専属の AI。呼び名はこれに統一
- 個別の調理場: バディが素材を子どもごとに調整する機能
- 提案箱: ファクトリーに題材を持ち込む入口の共通の受け口
- 編集基準: 運営の回答・承認・差し戻し理由を貯めたもの。職人が毎回読む
